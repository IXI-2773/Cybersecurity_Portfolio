The investigation

Can a compact packet analyzer surface a DNS failure burst and an unusual HTTP request while keeping the evidence traceable? I generated a deterministic PCAP, decoded the supported traffic, and compared candidate patterns against benign requests.

The training capture contains 20 Ethernet/IPv4 frames: ten DNS packets and ten TCP/HTTP packets. The bounded parser extracts 12 events and returns two review signals. Reserved addresses and hostnames keep the example self-contained.

The two findings

DNS: repeated name-resolution failures

Four NXDOMAIN replies are associated with client 192.0.2.10 within approximately 36 seconds. The threshold-crossing observation is at 12:00:36.200 UTC. This creates a DNS-review hypothesis; it does not demonstrate tunneling.

HTTP: a POST to the test collector

A POST to collector.invalid/upload appears at 12:01:15.030 UTC. The reserved hostname is part of the fixture. Request method and destination alone cannot establish command-and-control, sensitive content, or exfiltration.

The LAB-NET-001 report ↗ maps the observations to exact frames and timestamps, alongside the comparison traffic.

The analyst decision

Disposition: correlate before classifying. For comparable authorized telemetry, I would check resolver history, the originating process, proxy records, destination ownership, and any available request content. A benign failure burst or expected application request can change the interpretation.

WHY PACKET CONTEXT MATTERS

A rule can identify a pattern. The analyst still has to establish who generated it, what happened around it, and whether the proposed explanation fits.

Reproduce the capture

python projects/03-network-pcap/generate_fixture.py --output projects/03-network-pcap/synthetic_traffic.pcap
python projects/03-network-pcap/analyze_pcap.py projects/03-network-pcap/synthetic_traffic.pcap
python -m unittest discover -s projects/03-network-pcap -p 'test_*.py' -v

The generator produces a real PCAP binary with deterministic contents. The runbook ↗ records the expected hash and analysis steps. Eighteen tests cover expected findings, malformed captures, pairing, deduplication, isolation, and benign controls.

Scope and limits

The parser covers the packet forms in this fixture. It does not reassemble TCP streams or support TLS analysis, pcapng, fragmented IPv4, compressed DNS names, or IPv6. Wireshark GUI inspection remains pending. No real network packets or production incidents are represented.
