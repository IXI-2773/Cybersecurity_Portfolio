Linux access audit with SQL

Can I remove two unsafe access conditions without breaking the access that should remain?

From Linux modes to a SQL finding

Python inventories the three root-owned files using lstat. SQLite stores the measured modes as integers and joins them to a policy table by path. The bitwise predicate selects a file when any forbidden permission bit is present.

SELECT a.path, a.mode, p.forbidden_mask,
       p.target_mode, p.risk
FROM assets AS a
JOIN policies AS p ON p.path = a.path
WHERE (a.mode & p.forbidden_mask) != 0
ORDER BY a.path;

The secret policy forbids group/other read (0044). The script and notice policies forbid group/other write (0022). Octal modes are converted to integers before insertion; values enter SQLite through parameterized statements.

Only the matched paths receive their declared target modes. The second SQL pass returns zero findings under the same policies. The child-process tests then establish that the access change was enforced on this Linux runner.

The remediation decision

Restrict the secret to its owner. Its dummy token illustrates a confidentiality risk: another local user could open a file intended for the service owner. The 0600 target preserves owner read/write and removes group/other access.

Remove shared write access from the script. A script writable by other users creates an integrity risk if a trusted process later executes it. That later execution is a risk scenario, not an observed event here. The 0755 target keeps owner write and public read/execute while removing group/other write.

Retest the intended access too. The public notice must remain readable. Keeping that control prevents a blanket lock-down from appearing to be a successful fix. On a real system, I would confirm the service identity and required access with its owner before changing modes.

Scope and limits

Executed on three deliberately configured dummy files in a temporary directory. This demonstrates Linux permission analysis, SQL policy matching and a measured remediation retest. It is not employment experience or a production incident. No real credential was exposed.

Zero findings applies only to these policies and files. The lab does not assess ACLs, capabilities, privileged access, network services, application authorization or all ways a file can be replaced. The access probe verifies open permission; it does not execute the script or prove an application works. A restricted container can block the required UID/GID change; that failure produces no successful report.
