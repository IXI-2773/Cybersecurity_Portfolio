01 / HANDS-ON DEFENSIVE SECURITY LAB

Authentication Detection & Triage

An executable, synthetic security-operations exercise that flags repeated failed logins followed by a successful authentication.

Python standard library31 focused testsSynthetic eventsSplunk SPL concept

Question & threat hypothesis

Which successful logins occur after at least five failed attempts within ten minutes from the same username and source IP? This sequence can support investigation of MITRE ATT&CK T1110 (Brute Force), but does not prove compromise.

Detection design

  1. Parse and validate a strict, small CSV event schema.
  2. Sort by timestamp and maintain a rolling failure queue keyed by username and source IP.
  3. When a matching success follows a sufficient failure burst, record a contextual finding.
  4. Clear the burst after every success, even if it was below the alert threshold, so unrelated login streaks cannot contaminate one another.

Run it

cd projects/01-authentication-detection
python -m unittest -v
python detect_auth.py auth_events.csv

Expected finding: fabricated user alice, source 192.0.2.15, six failed logins before a success. The fixture contains deliberate non-alert sequences for other identities. IPs come from documentation ranges, not operational targets.

What was tested

True-positive fixture behavior; fewer than five failures; expired window; account and IP isolation; out-of-order events; inclusive time boundary; malformed timestamp; invalid configuration; login-streak reset; independent user histories; CSV row validation; and validation-matrix expectations.

Analyst response

Review MFA and identity-provider logs, source context, device/session details, time synchronization, user history, and correlated endpoint events. Escalate when independent evidence supports the finding; the threshold alone is insufficient.

Limitations & improvement path

  • False positives: legitimate typing errors and noisy authorized automation.
  • False negatives: rotating IPs, distributed attempts, missing events, misaligned clocks, and low-and-slow attempts.
  • The SPL design and runbook are inspectable; only a real authorized Splunk run and independently checked export can establish runtime equivalence.
  • No precision, recall, detection latency, or production effectiveness is claimed.

Investigation at a glance

Observed synthetic case: six failed logins from one account/source IP followed by a success at 09:06 UTC. The one finding is a review signal, not a compromise determination. Five expected findings across nine independent synthetic scenario families test the broader detection behavior.
