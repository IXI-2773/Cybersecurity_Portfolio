The investigation problem

A rule that matches a suspicious command or a login burst is a starting point. Its value depends on the behavior it is intended to detect, the data it needs and the legitimate activity that can produce the same pattern.

My lab work

My résumé describes developing and testing more than five SPL and Sigma rules for brute-force activity, Base64-encoded PowerShell and lateral movement. I simulated attack scenarios, mapped the detections to ATT&CK and documented their logic.

The tuning work focused on reducing false positives during lab validation. The approximately 30% reduction is the result reported in my résumé; the original before-and-after event sets will accompany the detailed evidence when organized.

The telemetry contract

The rule needs a valid UTC timestamp, username, source IP, host context, and a failure/success event type. It groups by username and source IP; the host is displayed as context. Every success closes that stream’s failure streak, even if no finding is produced. Events are ordered by timestamp, preserving source order on ties in this public fixture.

The browser rejects missing required fields and malformed times. In an operational pipeline, parser coverage, clock skew, duplicates, late arrival, and retention would need their own verification. A correct query cannot recover telemetry that was never collected.

Why the correction matters

A bucket edge can split related events. The corrected SPL calculates each preceding failure’s age at a successful login and explicitly includes the 600-second boundary. Interleaved accounts remain separate; failures from a different source IP cannot complete another stream’s threshold.

The minimum count is a triage heuristic. Raising it can reduce noise while missing slower attempts. A successful login after repeated failures can also be a legitimate user recovering access. MFA outcome, session history, account sensitivity, and related endpoint events determine the next investigation step.
