Splunk SOC investigation: detection to scheduled alert

A synthetic authentication pattern moved from source events to an indexed detection and one native fired-alert record, with a traceable analyst handoff.

Controlled lab confirmed November 8, 2026. The indexed search matched the expected data and a scheduled Splunk job fired once. This is not a real compromise or a production detection benchmark. New-run screenshots are still pending.

The case in 30 seconds

Five or more failed logins followed by a success for the same user and IP can be a credential-access investigation lead. I worked on the lab's exact ten-minute boundary, success reset, and negative checks. Its live confirmation indexed the original 64 fabricated events plus six fresh replay events, matched all five expected findings, and captured the scheduled search result before disabling the temporary alert.

The important result is a complete evidence path from fabricated input to an actual Splunk scheduling outcome—not evidence that an attacker gained access.

How I would investigate

Signal
At least five failures within an inclusive 600-second window, followed by a success; correlation is isolated by username and source IP, and an intervening success resets the streak.
Alternative explanations
Forgotten-password retries, password-manager errors, authorized recovery, stale service credentials, or shared network egress can produce a similar pattern.
Next analyst action
Verify MFA and session history, device identity, account-owner activity, source-IP context, and endpoint telemetry. Open a review ticket and escalate only if corroborating evidence and local procedures justify it.

No real account was locked, endpoint isolated, or notification sent in this lab.
